- **The ledger design.** `packages` (conversation, size, price_paise, payment_id, state CREATING → PENDING → PAID → CLOSED, or EXPIRED / FAILED, created_at) and `credits` (package_id, delta, reason PURCHASE | BOOK | CANCEL_RETURN | REFUND | ADJUST, session_id, at, by). **A balance is always `SUM(credits.delta)` over the person's packages; it is never stored.** Three unique partial indexes make replays harmless: one PURCHASE per package, one BOOK per session, one CANCEL_RETURN per session. Every change is one `db.batch` (one transaction) of statements that each write only if the rule still holds:
  - *Purchase:* the Razorpay link (no slot held, expires after 60 min) is a `payments` row with purpose PACKAGE and `target_id` = the package. A verified PAID event moves the package to PAID and adds the PURCHASE row (+N) in one batch; a replay, a second event for the same payment or the cron's status read changes nothing and sends nothing twice (confirmation dedupe key `paid:<payment id>`). A payment that arrives after the link expired still adds the credits (it is real money). A wrong amount is a `PAYMENT_MISMATCH` item and adds nothing. A second tap while a link is open shows `packPending` instead of making another link.
  - *Booking with a credit:* ONE batch: (1) insert the SESSION slot as BOOKED only if it is free of any call or session, the balance is above 0 and the buyer has fewer than 2 upcoming sessions (CREDIT_BOOKED or CONFIRMED, not ended); (2) insert the session (CREDIT_BOOKED, on the oldest package with credits left); (3) insert the −1 BOOK row; (4) free the slot again if (2) did not link it. A double tap, two taps at once, a replayed message: one credit, one slot (tested with two simultaneous taps and one credit left).
  - *Cancel (package session, ≥ 3 h):* session CANCELLED + slot freed + CANCEL_RETURN +1, one batch. *Move:* the new slot is booked, the session points at it, the old slot is freed, one batch; it needs ≥ 3 h to the old time, and a single session may be moved once. *Cancel (single, ≥ 24 h):* session CANCELLED + slot freed, then the one refund path (`requestRefund(..., "CANCEL")`, unique per payment; a failure to write the refund row raises `CANCEL_REFUND_FAILED`).
  - The boundaries are inclusive and counted from the session's start as an instant (IST has no daylight saving): exactly 3 h or 24 h before is allowed; one second less is not. Tested at both.

- `gate(env, conv, message)` returns the 13 values of the ticket **plus `TAP`** (a button, list or template quick-reply tap): taps are not "typed text", but they still have to pass the blocked / first-message / handoff / HUMAN checks, so the gate has to say "a tap". Order: safety (typed text only) -> blocked (IGNORE) -> first message (GREETING) -> opt-out -> handoff (button or words) -> HUMAN (HUMAN_WAIT) -> taps -> quiet period (IGNORE, or BOOKING_WORD) -> media -> ack words -> menu words -> "book" -> budget -> TO_CLASSIFIER. A WhatsApp reaction is IGNORE.
- Safety: matched on whole words/phrases after `normalize()` (lower case, NFC, nukta removed, ँ -> ं, punctuation and emoji removed, one space). Crisis: fixed message (language: Devanagari in the text -> Hindi; else the language the person chose; before they chose, English), CRISIS item, email "Urgent: crisis message" with only `<PUBLIC_URL>/admin` (sent when a new CRISIS item is raised, so a person who keeps writing does not flood Rohit), mode HUMAN (a BLOCKED chat stays BLOCKED), `no_sell_until` = now + 7 days, and the person counts as greeted (the bot's greeting never follows a crisis message). Emergency: fixed message + EMERGENCY item, no HUMAN mode, no email, no menu. Both go out through `sendMessage(..., { safety: true })`: they reach blocked people and ignore a paused SENDS switch. **When the SENDS env flag is not "true", safety does not run at all** (AGENT §3.2 word for word: that Worker cannot send; the message is then handled like any other and a CRISIS item is not raised). Resolving a CRISIS item in /admin hands the chat back to the bot (like HUMAN_REQUEST); `no_sell_until` stays until it runs out or Rohit clears it on the person's page.
- Per-person state `person_state` (ISO UTC; days are India days): the 13 columns of the ticket, plus `flirt_offences`, `abuse_offences` (for "a second offence") and `book_tap_at` (warm leads). Strikes clear on payment (`paymentCleared`, called when a verified payment is applied; it also ends a quiet period) or when the last strike is more than 7 days old. Three strikes: `quietClose` once, `quiet_until` = +7 days, strikes back to 0; a second quiet period within 30 days is a block `NOISE_REPEAT`. Flirt: one line + strike, block `NOISE_SEXUAL` on an `sexualBlockWords` match or a second offence; abuse: strike + no reply, block `NOISE_ABUSE` on an `abuseBlockWords` match or a second offence; spam: strike + no reply; smalltalk: 2 free per India day. Paying customers (`isPayingCustomer`: a PAID/CONFIRMED/RESCHEDULED call or session, or a PAID payment, in the last 30 days; a hold is not enough) get no strikes, no quiet period, no block and are never IGNOREd in a quiet period. Blocks written by the bot have `by = 'system'`.
- Rule-based classifier `classifyWithoutAI`: abuse (`abuseBlockWords` + `abuseWords`), flirt/sexual (`sexualBlockWords` + `flirtWords`), spam (a link and a `spamWords` word); everything else is TO_CLASSIFIER and gets today's ack (once per 24h) + a FREE_TEXT item.
